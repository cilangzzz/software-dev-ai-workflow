# 流程规范：需求梳理

## 基本信息

| 属性 | 值 |
|------|-----|
| 流程名称 | 需求梳理 |
| 所属阶段 | 迭代规划阶段 |
| 流程负责人 | 产品负责人 |
| 前置流程 | Sprint0准备 |
| 后置流程 | 故事拆分 |

## 流程目的

精化Product Backlog，确保用户故事清晰、可估算、可执行，为迭代计划会议做准备。

## 触发条件

- Product Backlog已创建
- 迭代即将开始（通常提前1-2天）
- 新需求加入Product Backlog

## 输入物

| 输入物 | 来源 | 必要性 |
|--------|------|--------|
| Product Backlog | 项目启动阶段 | 必须 |
| 用户反馈 | 用户/干系人 | 建议 |
| 业务变更 | 业务部门 | 建议 |

## 执行步骤

### Step 1: Backlog健康检查

- [ ] 检查Product Backlog数量
- [ ] 确认优先级排序正确
- [ ] 识别过时或重复的需求
- [ ] 标记需要精化的故事

### Step 2: 用户故事精化

- [ ] 检查用户故事是否符合INVEST原则
- [ ] 确保用户故事有清晰的验收标准
- [ ] 补充缺失的用户故事描述
- [ ] 拆分过大的用户故事（Epic）

### Step 3: 验收标准编写

- [ ] 为每个用户故事编写验收标准
- [ ] 确保验收标准可测试
- [ ] 使用Gherkin格式（Given-When-Then）
- [ ] 涵盖正常和异常场景

### Step 4: 初步估算

- [ ] 对用户故事进行Story Point估算
- [ ] 使用规划扑克（Planning Poker）方法
- [ ] 记录估算结果
- [ ] 标记估算不确定的故事

### Step 5: 优先级调整

- [ ] 根据业务价值调整优先级
- [ ] 考虑依赖关系
- [ ] 考虑风险因素
- [ ] 确保高优先级故事已精化

### Step 6: Backlog评审

- [ ] 组织Backlog精化会议（时间盒：1-2小时）
- [ ] 与团队确认故事理解一致
- [ ] 记录疑问和待确认项
- [ ] 更新Product Backlog

| 验收标准 | 文档/工具 | 项目管理工具 |
| Story Point估算 | 文档/工具 | 项目管理工具 |

## 质量标准

- Product Backlog高优先级故事已精化
- 用户故事符合INVEST原则
- 每个用户故事有明确的验收标准
- Story Point估算误差范围在合理范围内

## 异常处理

| 异常场景 | 处理方式 |
|---------|---------|
| 故事过大无法估算 | 标记为Epic，安排拆分 |
| 验收标准不清晰 | 与产品负责人确认 |
| 依赖关系复杂 | 标记依赖，调整优先级 |
| 需求变更频繁 | 建立需求变更流程 |

## INVEST原则

| 原则 | 说明 |
|------|------|
| Independent | 独立：用户故事之间相互独立 |
| Negotiable | 可协商：故事内容可以讨论和调整 |
| Valuable | 有价值：对用户或业务有价值 |
| Estimable | 可估算：能够估算工作量 |
| Small | 小：在一个迭代内可以完成 |
| Testable | 可测试：有明确的验收标准 |
