# 流程规范：改进措施落地

## 基本信息

| 属性 | 值 |
|------|-----|
| 流程名称 | 改进措施落地 |
| 所属阶段 | 迭代回顾 |
| 流程负责人 | 改进项负责人 |
| 前置流程 | 改进项识别 |
| 后置流程 | 下一迭代回顾验证 |
| 执行周期 | 持续（直至改进项完成） |

## 流程目的

将识别的改进项转化为可执行的具体行动，跟踪执行进度，验证改进效果，形成持续改进闭环。

## 触发条件

- 改进项识别完成
- 改进项已确定优先级
- 已指定负责人

## 输入物

| 输入物 | 来源 | 必要性 |
|--------|------|--------|
| 改进项列表 | 改进项识别 | 必须 |
| 团队资源情况 | 迭代规划 | 必须 |
| 历史改进效果 | 历史记录 | 建议 |

## 执行步骤

### Step 1: 制定Action Items

为每个改进项制定具体的行动项：

```markdown
## Action Item 模板

### 基本信息
- **关联改进项**：IMP-XXX
- **行动项编号**：ACT-XXX
- **负责人**：姓名
- **截止日期**：YYYY-MM-DD

### 行动内容
- **具体行动**：xxx
- **完成标准**：xxx
- **验收方法**：xxx

### 资源需求
- **时间投入**：X人日
- **需要支持**：xxx
- **依赖条件**：xxx

### 进度跟踪
- **状态**：待开始/进行中/已完成/验证中
- **当前进度**：X%
- **阻塞问题**：xxx
```

### Step 2: SMART原则检查

确保每个Action Item符合SMART原则：

| 原则 | 检查项 | 示例 |
|------|--------|------|
| Specific（具体） | 行动是否具体明确？ | "优化代码评审流程" → "每次PR至少需要1个评审人，24小时内完成" |
| Measurable（可衡量） | 如何衡量完成？ | "完成率80%" → "5次评审中4次在24小时内完成" |
| Achievable（可达成） | 团队有能力完成吗？ | 评估资源和能力 |
| Relevant（相关） | 是否解决改进项？ | 与改进项问题关联 |
| Time-bound（有时限） | 有明确截止时间吗？ | 设置具体日期 |

### Step 3: 纳入迭代计划

- [ ] 将Action Items添加到下迭代待办
- [ ] 评估对迭代容量的影响
- [ ] 与产品负责人协调优先级
- [ ] 确保改进项可见性

### Step 4: 执行跟踪

#### 每日站会跟踪
- 报告Action Items进度
- 识别阻塞问题
- 协调资源支持

#### 周度检查
- 更新Action Items状态
- 评估是否有新阻塞
- 调整计划如需要

#### 看板可视化
```
| 待开始 | 进行中 | 已完成 | 验证通过 |
|-------|-------|-------|---------|
| ACT-001 | ACT-002 | ACT-003 | ACT-004 |
```

### Step 5: 效果验证

在下次回顾会议验证：

| 验证维度 | 检查项 |
|---------|-------|
| 完成情况 | Action Item是否按时完成？ |
| 效果达成 | 改进项问题是否解决？ |
| 持续性 | 改进是否可持续？ |
| 副作用 | 是否带来新问题？ |

### Step 6: 关闭或调整

**关闭条件：**
- Action Items已完成
- 效果已验证
- 无遗留问题

**调整条件：**
- 未达到预期效果
- 需要继续改进
- 发现更好方案

## Action Items优先级

| 优先级 | 说明 | 处理方式 |
|--------|------|---------|
| P0 | 阻塞团队效率，必须解决 | 立即处理，本迭代内完成 |
| P1 | 影响效率，需要解决 | 纳入下迭代计划 |
| P2 | 有改进价值，可延后 | 放入改进项池，择机处理 |

## 改进效果评估

### 量化指标

| 改进类型 | 评估指标 |
|---------|---------|
| 效率改进 | 处理时间、吞吐量 |
| 质量改进 | 缺陷数、返工率 |
| 协作改进 | 响应时间、满意度 |
| 流程改进 | 周期时间、等待时间 |

### 效果评估模板

```markdown
## 改进效果评估

### 基本信息
- **改进项编号**：IMP-XXX
- **评估日期**：YYYY-MM-DD
- **评估人**：姓名

### 效果评估
- **目标达成度**：完全达成/部分达成/未达成
- **量化指标**：
  - 改进前：xxx
  - 改进后：xxx
  - 变化：+/-X%

### 持续性评估
- 是否形成规范/流程？是/否
- 是否需要持续关注？是/否
- 团队接受度：高/中/低

### 经验总结
- 有效做法：xxx
- 注意事项：xxx
- 推广建议：xxx

### 后续行动
- [ ] 关闭改进项
- [ ] 继续优化（具体措施：xxx）
- [ ] 转为长期改进
```

## 输出物

| 输出物 | 格式 | 存放位置 |
|--------|------|---------|
| Action Items | 任务/表格 | 任务管理系统 |
| 改进效果评估 | 文档 | 项目文档库 |
| 更新的改进项列表 | 文档/表格 | 项目文档库 |

## 质量标准

### Action Items质量标准
- 符合SMART原则
- 有明确负责人
- 有具体截止日期
- 有可验证的完成标准

### 执行跟踪标准
- 每日更新进度
- 阻塞问题及时上报
- 状态变化及时通知

### 效果验证标准
- 有量化数据支撑
- 有团队反馈确认
- 有持续性保障

## 改进项生命周期

```
识别 → 评估 → 制定措施 → 执行 → 验证 → 关闭/调整
  ↑                                        ↓
  └──────────── 效果不达标继续优化 ←───────┘
```

## 异常处理

| 异常场景 | 处理方式 |
|---------|---------|
| Action Item无法按时完成 | 评估原因，调整计划或寻求帮助 |
| 效果不明显 | 分析根因，调整措施 |
| 阻塞无法解决 | 升级到管理层，或调整改进项 |
| 资源不足 | 与产品负责人协商，调整迭代内容 |

## 最佳实践

### 保持节奏
- 每迭代改进少量项，持续积累
- 不追求大而全，注重小步快跑
- 改进项数量可控，确保落地

### 可视化
- 使用看板展示改进项状态
- 在团队空间展示改进进度
- 每日站会报告进度

### 庆祝成功
- 改进效果达成时庆祝
- 分享成功经验
- 认可团队贡献

### 持续迭代
- 改进是持续过程，不是一次性项目
- 每迭代都应有改进
- 形成改进文化
