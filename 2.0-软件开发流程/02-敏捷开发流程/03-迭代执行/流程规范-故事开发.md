# 流程规范：故事开发

## 基本信息

| 属性 | 值 |
|------|-----|
| 流程名称 | 故事开发 |
| 所属阶段 | 迭代执行 |
| 流程负责人 | 研发工程师 |
| 前置流程 | 任务分配 |
| 后置流程 | 故事验收 |

## 流程目的

按照用户故事和验收标准完成功能开发，确保代码质量和功能正确性。

## 触发条件

- 用户故事已分配
- 验收标准明确
- 开发环境就绪

## 输入物

| 输入物 | 来源 | 必要性 |
|--------|------|--------|
| 用户故事 | 迭代规划 | 必须 |
| 验收标准 | 迭代规划 | 必须 |
| 技术设计 | 迭代规划 | 建议 |
| 编码规范 | 项目规范 | 必须 |

## 执行步骤

### Step 1: 故事理解

- [ ] 阅读用户故事描述
- [ ] 理解验收标准
- [ ] 确认技术方案
- [ ] 识别依赖关系

### Step 2: 任务拆分

- [ ] 将故事拆分为技术任务
- [ ] 估算任务工时
- [ ] 更新任务看板
- [ ] 标记任务依赖

### Step 3: 开发环境准备

- [ ] 拉取最新代码
- [ ] 创建开发分支
- [ ] 安装依赖包
- [ ] 启动开发环境

### Step 4: 编码实现

#### 4.1 核心功能开发

- [ ] 编写业务代码
- [ ] 实现核心逻辑
- [ ] 处理异常情况

#### 4.2 单元测试编写

- [ ] 编写单元测试用例
- [ ] 覆盖核心逻辑
- [ ] 验证边界条件

#### 4.3 代码提交

- [ ] 代码格式化
- [ ] 本地测试通过
- [ ] 编写提交信息
- [ ] 推送代码

### Step 5: 代码审查

- [ ] 创建合并请求(MR/PR)
- [ ] 填写变更说明
- [ ] 关联故事编号
- [ ] 等待审查反馈

### Step 6: 修改完善

- [ ] 处理审查意见
- [ ] 修改代码问题
- [ ] 补充测试用例
- [ ] 再次提交审查

### Step 7: 合并代码

- [ ] 审查通过
- [ ] 合并到开发分支
- [ ] 触发CI构建
- [ ] 验证构建成功

### Step 8: 故事验收准备

- [ ] 更新故事状态
- [ ] 准备演示环境
- [ ] 编写演示步骤
- [ ] 申请故事验收

## 输出物

| 输出物 | 格式 | 存放位置 |
|--------|------|---------|
| 源代码 | 代码 | 代码仓库 |
| 单元测试 | 代码 | 代码仓库 |
| 合并请求 | 记录 | 代码仓库 |
| 开发日志 | 文档 | 项目管理工具 |

## 质量标准

### 代码质量

- 符合编码规范
- 无代码异味
- 代码审查通过

### 测试质量

- 单元测试覆盖率≥80%
- 核心逻辑100%覆盖
- 边界条件已测试

### 功能质量

- 满足验收标准
- 自测功能正常
- 无明显Bug

## 开发分支策略

| 分支类型 | 命名规则 | 用途 |
|---------|---------|------|
| 功能分支 | feature/story-id-description | 开发新功能 |
| 修复分支 | fix/bug-id-description | 修复Bug |
| 发布分支 | release/version | 发布准备 |

## 提交信息规范

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Type类型

| Type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档更新 |
| style | 代码格式 |
| refactor | 重构 |
| test | 测试 |
| chore | 构建/工具 |

## 相关Skill

| Skill | 用途 |
|-------|------|
| implement | 功能实现辅助 |
| code-review | 代码审查 |
| unit-test | 单元测试 |

## 异常处理

| 异常场景 | 处理方式 |
|---------|---------|
| 需求理解偏差 | 与产品确认后调整 |
| 技术方案受阻 | 寻求技术支持 |
| 任务超时 | 及时上报，调整计划 |
| 依赖阻塞 | 协调依赖方解决 |
