# 敏捷度量体系

## 概述

敏捷度量体系用于评估敏捷团队的交付效率、质量和健康状态，帮助团队持续改进。

## 核心度量指标

### 1. Velocity（速率）

| 属性 | 说明 |
|------|------|
| 定义 | 团队每个迭代完成的用户故事点数 |
| 计算 | 完成故事点数总和 |
| 用途 | 评估团队交付能力，预测未来迭代交付量 |
| 建议 | 关注趋势而非单点值，排除异常迭代 |

**示例计算：**
```
迭代1: 完成 25 SP
迭代2: 完成 28 SP
迭代3: 完成 30 SP
平均Velocity: 27.67 SP/迭代
```

### 2. Lead Time（前置时间）

| 属性 | 说明 |
|------|------|
| 定义 | 需求从提出到交付上线的时间 |
| 计算 | 交付日期 - 需求提出日期 |
| 用途 | 评估需求响应速度 |
| 建议 | 缩短Lead Time是敏捷核心目标 |

**示例计算：**
```
需求提出: 2026-01-01
交付上线: 2026-01-15
Lead Time: 14天
```

### 3. Cycle Time（周期时间）

| 属性 | 说明 |
|------|------|
| 定义 | 用户故事从开发开始到完成的时间 |
| 计算 | 完成日期 - 开发开始日期 |
| 用途 | 评估开发效率，识别瓶颈 |
| 建议 | Cycle Time应小于迭代周期 |

**示例计算：**
```
开发开始: 2026-01-05
开发完成: 2026-01-12
Cycle Time: 7天
```

### 4. Sprint Burndown（迭代燃尽）

| 属性 | 说明 |
|------|------|
| 定义 | 迭代剩余工作量随时间变化的曲线 |
| 计算 | 每日剩余故事点数 |
| 用途 | 监控迭代进度，预警延期风险 |
| 建议 | 理想线应平稳下降至零 |

### 5. Defect Rate（缺陷率）

| 属性 | 说明 |
|------|------|
| 定义 | 交付后发现的缺陷数量占比 |
| 计算 | 迭代后缺陷数 / 交付故事数 |
| 用途 | 评估交付质量 |
| 建议 | 目标<5%缺陷率 |

### 6. Team Happiness（团队满意度）

| 属性 | 说明 |
|------|------|
| 定义 | 团队成员对工作状态的满意度 |
| 计算 | 定期问卷调查（1-5分） |
| 用途 | 评估团队健康状态 |
| 建议 | 维持在3.5分以上 |

## 辅助度量指标

| 指标 | 说明 |
|------|------|
| 故事完成率 | 完成故事数/承诺故事数 |
| 迭代稳定性 | Velocity波动程度 |
| 代码覆盖率 | 单元测试覆盖比例 |
| 发布频率 | 单位时间内发布次数 |
| 平均修复时间 | MTTR（Mean Time To Repair） |

## 度量实施建议

### 数据收集方式
- **自动化**: CI/CD系统自动记录部署时间、测试覆盖率
- **工具辅助**: Jira/Azure DevOps记录故事状态变化时间
- **人工填报**: 团队满意度定期问卷

### 度量频率
- Velocity、Burndown: 每迭代
- Lead Time、Cycle Time: 每需求
- Team Happiness: 每月
- Defect Rate: 每发布

### 度量原则
1. **度量驱动改进**: 数据用于发现问题，而非考核个人
2. **关注趋势**: 单点数据易波动，关注长期趋势
3. **团队共识**: 度量定义需团队共同理解和接受
4. **适度度量**: 避免过度度量导致负担
