# 流程规范：改进项识别

## 基本信息

| 属性 | 值 |
|------|-----|
| 流程名称 | 改进项识别 |
| 所属阶段 | 迭代回顾 |
| 流程负责人 | Scrum Master |
| 前置流程 | 回顾会议 |
| 后置流程 | 改进措施落地 |
| 建议时长 | 15分钟（融入回顾会议） |

## 流程目的

从回顾会议讨论中识别、分类和优先级排序改进项，确保改进机会不被遗漏。

## 触发条件

- 回顾会议讨论阶段完成
- 团队收集了足够的观察和想法

## 输入物

| 输入物 | 来源 | 必要性 |
|--------|------|--------|
| 回顾讨论记录 | 回顾会议 | 必须 |
| 迭制度量数据 | 敏捷度量体系 | 建议 |
| 历史改进项 | 改进项列表 | 建议 |

## 执行步骤

### Step 1: 汇总讨论结果

- [ ] 整理所有便签/记录
- [ ] 去除重复项
- [ ] 归类相似问题
- [ ] 确认理解一致

### Step 2: 识别改进项类型

按影响范围分类：

| 类型 | 说明 | 示例 |
|------|------|------|
| 团队协作 | 团队内部协作问题 | 沟通不畅、职责不清 |
| 流程方法 | 工作流程问题 | 需求变更频繁、评审效率低 |
| 技术实践 | 技术层面问题 | 代码质量、技术债务 |
| 工具环境 | 工具和环境问题 | 开发环境、CI/CD效率 |
| 外部依赖 | 团队外部问题 | 其他团队配合、资源等待 |

### Step 3: 评估改进项

使用影响矩阵评估：

| 维度 | 问题 | 评分（1-5） |
|------|------|------------|
| 影响程度 | 对团队效率的影响有多大？ | 1-5 |
| 发生频率 | 多久发生一次？ | 1-5 |
| 可控程度 | 团队可以控制吗？ | 1-5 |
| 投入成本 | 解决需要多少投入？ | 1-5（反向） |

**优先级计算：** 影响 × 频率 × 可控 × 成本 = 优先级分数

### Step 4: 投票确定优先级

- [ ] 每人获得3-5张投票
- [ ] 投票给认为最重要的改进项
- [ ] 统计得票数
- [ ] 确定Top 3-5改进项

### Step 5: 详细描述改进项

为每个高优先级改进项填写：

```markdown
## 改进项编号：IMP-XXX

### 描述
- **问题现象**：xxx
- **影响范围**：xxx
- **期望状态**：xxx

### 根因分析
- 为什么会出现这个问题？
- 5 Whys 分析

### 影响评估
- 影响程度：高/中/低
- 发生频率：频繁/偶尔/罕见
- 可控程度：可控/部分可控/不可控

### 优先级
- 得票：X票
- 优先级：P0/P1/P2
```

## 改进项分类模板

### 按来源分类

| 来源 | 编号前缀 | 说明 |
|------|---------|------|
| 回顾会议 | RET-XXX | 回顾会议识别 |
| 日常发现 | DLY-XXX | 日常工作发现 |
| 度量分析 | MET-XXX | 度量数据分析 |
| 事故复盘 | INC-XXX | 事故复盘结果 |

### 按状态分类

| 状态 | 说明 | 后续动作 |
|------|------|---------|
| 新建 | 刚识别，待评估 | 评估优先级 |
| 待处理 | 已评估，待制定措施 | 制定Action Items |
| 进行中 | 正在执行 | 跟踪进度 |
| 已完成 | 措施已执行 | 验证效果 |
| 验证通过 | 效果已确认 | 关闭改进项 |
| 搁置 | 暂不处理 | 定期回顾 |

## 质量标准

### 改进项描述标准
- 问题现象描述具体
- 影响范围明确
- 期望状态清晰
- 可衡量可验证

### 优先级评估标准
- 多维度评估，不仅凭主观感受
- 投票过程公平透明
- 高优先级项数量可控（每迭代≤3个）

## 改进项数量控制

| 迭代周期 | 新增改进项上限 | 同时进行项上限 |
|---------|--------------|--------------|
| 1周 | 2个 | 3个 |
| 2周 | 3个 | 5个 |
| 4周 | 5个 | 7个 |

## 相关Skill

| Skill | 用途 |
|-------|------|
| retro-facilitator | 回顾会议引导 |
| action-tracker | 改进项跟踪 |

## 异常处理

| 异常场景 | 处理方式 |
|---------|---------|
| 改进项过多 | 投票筛选，其余入改进项池 |
| 改进项模糊 | 追问细节，明确问题 |
| 全是外部问题 | 关注可控部分，识别间接影响 |
| 无改进项 | 回顾改进项池，或深入挖掘 |

## 最佳实践

### 避免的陷阱
- 不要只识别问题，要识别改进机会
- 不要只关注负面，要保留好的做法
- 不要改进项堆积，要控制数量
- 不要忽略外部反馈，要主动收集

### 有效识别技巧
- 使用5 Whys深挖根因
- 关注数据而非感受
- 从客户视角思考
- 关注流程而非个人
